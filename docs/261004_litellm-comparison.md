# Hook Router와 LiteLLM: 차이와 선택적 업무 위임의 장점

2026-10-04 기준. Hook Router의 현재 구현과 LiteLLM 공식 문서를 비교한다. 비용 절감률이나 정확도를 측정한 벤치마크는 아니다.

## 요약

Hook Router의 핵심 장점은 **Codex의 부모 대화를 유지하면서, 사용자가 선택한 요청만 업무 단계별로 나누어 다른 Codex 작업 모델에 맡기는 것**이다. 일반 대화와 어려운 판단은 부모 모델로 진행하고, 반복 업무를 위임할 때 `@route`를 선택할 수 있다.

LiteLLM도 Codex의 모델 제공자로 연결할 수 있다. 따라서 “LiteLLM을 쓰려면 Codex 에이전트나 세션을 포기해야 한다”는 설명은 틀리다. LiteLLM은 모델 요청을 중계하고, 그 앞의 Codex가 도구 실행·반복 작업·세션을 관리할 수 있다. [LiteLLM의 Codex 연결 가이드](https://docs.litellm.ai/docs/proxy/client_setup/codex_cli)

## 1. 실행 경로

### Hook Router

```text
일반 입력
  → 부모 Codex 모델이 처리

@route + 요청
  → UserPromptSubmit 훅
  → 라우터가 업무 순서와 모델 배정 계획 생성
  → Python이 계획 검증
  → codex exec / resume로 작업 단계 순차 실행
  → 결과를 부모 모델에 전달
  → 부모가 사용자에게 보고
```

훅은 입력 제출 이벤트에서 호출되지만, 라우팅 실행은 정해진 접두어나 플러그인 멘션으로 시작한 요청에 한정된다. 일반 입력에서는 라우터 모델을 호출하지 않는다. 작업 모델도 Codex 에이전트로 실행되므로 파일 조회·도구 실행·여러 차례의 판단을 수행할 수 있다. 동일한 부모 세션에 연결된 작업 스레드는 후속 단계와 요청에서 재개한다.

### Codex + LiteLLM

```text
사용자 요청
  → Codex 에이전트
  → 모델 응답이 필요할 때마다 LiteLLM 게이트웨이로 요청
  → 지정 모델 또는 Auto Router가 선택한 모델
  → Codex가 응답에 따라 도구 실행·후속 요청
```

Codex의 모델 제공자로 LiteLLM을 설정하면 해당 제공자를 사용하는 세션의 모델 요청이 게이트웨이를 거친다. `@route` 같은 접두어는 필요하지 않다. 특정 모델을 지정할 수도 있고, Auto Router를 지정해 요청별 모델 선택을 맡길 수도 있다. **LiteLLM을 거친다는 사실 자체가 자동 모델 선택을 뜻하지는 않는다.** [Codex 제공자 설정](https://docs.litellm.ai/docs/proxy/client_setup/codex_cli)

## 2. 무엇을 기준으로 모델을 선택하는가

| 항목 | Hook Router | LiteLLM |
|---|---|---|
| 적용 범위 | 사용자가 `@route`로 선택한 요청 | LiteLLM 제공자로 보내는 모델 요청 |
| 배정 단위 | 사용자 요청에서 분리한 업무 단계 | 게이트웨이에 도착한 모델 요청; 설정에 따라 세션 선택 유지 가능 |
| 배정 기준 | 개인 설정의 `profiles[].description`과 사용자 명시 지시 | 기본 라우터의 운영 기준 또는 Auto Router의 분류 기준 |
| 기준 사용자 지정 | 모델·추론 수준·업무 설명 설정 | 모델 그룹·전략·등급별 모델·사용자 정의 분류 설정 |
| 순서와 상태 | 업무 계획, 순차 실행, 완료 기록, 재개를 직접 관리 | 이 비교의 게이트웨이 구성에서는 에이전트 실행 순서를 Codex가 관리 |
| 부모와 작업 세션 | 부모 대화와 별도 작업 스레드 | 기본 연결만으로 별도 부모–작업 스레드를 만들지는 않음 |

LiteLLM 기본 라우터는 모델 그룹 내 배포를 비용·지연·사용량·부하·가중치 등의 기준으로 선택한다. Auto Router는 휴리스틱, 키워드 규칙, LLM 또는 별도 분류기를 이용해 요청을 분류하고 설정한 등급의 모델을 선택할 수 있다. 세션 고정과 작업 정체 시 상위 등급 선택 같은 기능도 있으므로 LiteLLM을 단순 무작위 분산기로 설명하면 안 된다. Auto Router는 공식 문서에서 Add-on으로 안내된다. [기본 라우터](https://docs.litellm.ai/docs/routing), [Auto Router](https://docs.litellm.ai/docs/auto_router)

## 3. Hook Router가 유용한 상황

### 필요한 요청만 위임

부모 모델과 어려운 문제를 논의하다가, 반복 조회·정리 업무만 `@route`로 넘길 수 있다. 사용자는 자동 배정이 적용되는 경계를 직접 선택한다. 부모의 기본 모델을 매번 변경할 필요도 없다.

예를 들어 다음 요청을 처리할 수 있다.

```text
@route 받은편지함을 요약하고, 새 실험 결과의 타당성을 검토한 뒤,
검토 결과를 바탕으로 답장 초안을 작성해. 발송하지 마.
```

설정에 따라 아래처럼 나눠 실행한다.

```text
요약: Sol low → 실험 검토: Sol medium → 답장 초안: Sol low
```

같은 모델을 쓰는 인접 업무만 묶으므로 답장 작성이 연구 검토보다 먼저 실행되지 않는다. Python이 원문 누락·재작성·순서 변경과 허용되지 않은 모델 조합을 검사한다. 업무 의미를 올바르게 나눴는지는 여전히 라우터 판단에 달려 있다.

### Codex 에이전트 실행 기능 재사용

작업 모델을 API로 한 번 호출해 답변만 받는 방식과 달리, `codex exec`가 도구 실행과 반복 처리를 담당한다. 단계 사이에는 동일 작업 스레드를 재개해 앞선 결과를 활용한다. 코드가 완료 단계와 미완료 단계를 기록하고 중단·재개를 관리한다.

다만 현재 실행기는 `--ignore-user-config`를 사용하고 자식의 hooks·apps·multi_agent를 비활성화한다. **부모의 모든 MCP·앱·확장 설정이나 전체 대화가 그대로 전달되는 것은 아니다.** 필요한 업무 지침과 스킬 접근은 작업 설정으로 제공해야 한다. 이 경계는 [실행 코드](../hook_router/processes.py)와 [작업 프롬프트](../hook_router/engine.py)에 명시되어 있다.

### 별도 게이트웨이 없이 사용

현재 구조는 로컬 Python 표준 라이브러리와 Codex CLI로 실행한다. 기존 Codex 인증과 외부의 개인 설정·상태 파일을 활용한다. 여러 제공자의 API·키·게이트웨이를 운영할 필요가 없는 사용자에게는 설치와 운영 요소가 적다.

반면 여러 제공자, 조직별 예산과 관측, 분산과 장애 대응을 관리하려면 LiteLLM의 범위가 더 넓다. [LiteLLM 라우터 기능](https://docs.litellm.ai/docs/routing)

## 4. 성능 저하와 토큰 비용의 한계

**어려운 작업을 쉬운 모델로 잘못 보내는 위험은 양쪽 모두 있다.** 짧은 “확인해”가 앞선 맥락에서는 어려운 검증일 수 있다. Hook Router의 선택적 진입은 오분류가 적용되는 범위를 줄여 주지만, 호출한 요청 안에서의 오분류까지 없애지는 않는다.

중요한 요청에는 지원되는 모델·추론 수준을 명시할 수 있다. 다만 현재 구현은 허용된 조합과 계획 구조를 코드로 강제하며, 자연어 배정 지시를 정확히 따랐는지까지 별도 규칙으로 강제하지는 않는다.

토큰 비용은 대략 다음 항목으로 나뉜다.

```text
라우터 분류 + 각 작업 모델의 입력·추론·출력 + 부모 모델의 결과 수신·전달
```

- 고성능 부모 모델이 수행할 반복적인 도구 호출과 판단을 저렴한 작업 모델로 옮기면 비용이나 사용 한도를 아낄 가능성이 있다.
- 라우터 호출, 작업 지침·스킬 읽기, 누적 작업 기록, 결과 전달 비용은 남는다.
- 짧고 쉬운 요청 하나는 직접 처리보다 느리거나 비쌀 수 있다.
- 같은 스레드를 재개한다고 이전 문맥의 처리 비용이 항상 사라지는 것은 아니다. 캐시 적용도 별도 고려해야 한다.
- 플러그인 등록과 Python 코드 실행 자체는 모델 호출을 추가하지 않는다. 이름·설명·멘션이 모델 입력에 포함되면 소량의 토큰이 생길 수 있다.
- 정액제 사용 한도 절감률을 API 가격 비율과 동일하게 계산할 수는 없다.

따라서 “토큰 낭비 제거”나 “항상 저렴함”을 보장하지 않는다. 같은 업무를 직접 실행한 경우와 비교해 완료 품질, 시간, 모델별 사용량, 재시도·수정량을 함께 측정해야 한다.

## 5. 대체 관계인가

모델 연결과 요청별 선택만 필요하면 Codex + LiteLLM 구성이 충분할 수 있다. 사용자 요청의 사전 업무 분해, 순서 검증, 별도 작업 스레드, 완료 체크포인트, 부모 전달까지 원한다면 게이트웨이 연결 외에 그 실행 로직이 필요하다.

두 방식을 조합하는 설계도 가능하다. 하지만 현재 Hook Router는 사용자 제공자 설정을 상속하지 않으므로 LiteLLM 설정만 추가한다고 작업 모델이 자동으로 게이트웨이를 쓰지는 않는다. 조합하려면 제공자·인증·모델 메타데이터 전달을 명시적으로 구현하고 검증해야 한다.

**현재 플러그인의 실용적인 장점은 Codex의 부모 대화를 유지하고, 사용자가 선택한 복합 요청을 업무별 모델에 순서대로 위임하는 데 있다.**
